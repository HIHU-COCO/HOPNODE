## Linux race 首次失败与修复复测

同日集成方在 Linux 首次追加 `go test -race ./...` 检查，结果 **FAIL（DATA RACE）**。此前 Windows 普通 test/vet PASS 不足以发现该问题。原测试 `lockedBuffer` 匿名嵌入 `bytes.Buffer`，意外向外暴露其 `ReadFrom`；`os/exec` 的 `io.Copy` 走 `ReadFrom` 快路径，绕过包装器 `Write` 的锁，与测试中的 `text()` 并发读取发生竞争。

修复提交 `e030b1da9a4fe791b6a8fd5bd84aeb205650caf0` 将匿名嵌入改为未导出命名字段 `buffer bytes.Buffer`。仅由加锁的 `Write` 与 `text` 访问底层 buffer，不提供 `ReadFrom`，使 `io.Copy` 经过加锁的 `Write`。不改变协议服务或生产接口。

修复后在 POC 工作树重新执行：

## Windows Codex 真实模型调用

本次使用已有授权认证和 provider 的 Codex CLI。命令由隐藏的 PowerShell 工作进程执行，180 秒硬上限，只允许超时清理本次工作进程树。实际核心命令如下，路径占位符均解析为本次独有的可执行文件/trace/空临时目录；可执行复现见 POC README：

```text
codex -a never
  -c "mcp_servers={hopnode={command='<stdio-relay.exe>',args=['--target','<hopnode-poc.exe>','--trace','<new-handshake.jsonl>'],enabled=true,startup_timeout_sec=15,tool_timeout_sec=20}}"
  -c project_doc_max_bytes=0
  exec --ephemeral --json -s read-only --skip-git-repo-check --color never -C <empty-TEMP-directory> -
```

提示只允许按顺序调用 `hopnode.poc_probe`：`device_id=poc-local,action=echo,message=HOPNODE_P03_CODEX_20261019`；相同目标 `action=fail`（预期错误，不重试）；然后相同目标 `action=status`。禁止其他工具和文件访问。当前进程整体覆盖 `mcp_servers`，没有持久化注册，没有更改既有审批策略，也没有使用危险 bypass 参数。使用 `--ignore-user-config` 会丢失现有 provider，因此本次没有使用。

### 第一轮：实际握手成功，工具因审批被拒

17 秒退出 0、未超时。真实 Codex 加载 hopnode 并协商成功，但唯一 echo 事件为 `failed`，错误分类包含 `requires approval`；fail/status 未运行。CLI exit 0 只代表模型轮次正常结束，不能将这一轮工具调用算作 PASS。

夹具原先缺少能力提示。其 echo/fail/status/可取消 wait 均不写入外部文件、网络或设备，仅有内部测试序号/取消计数，故补充 SDK 真实元数据 `ReadOnlyHint=true`、`DestructiveHint=false`、`OpenWorldHint=false`。此变化只描述本地夹具，不能作为生产工具的通用属性，也没有放宽用户既有审批策略。SDK 子进程测试已校验 tools/list 中这三个属性。

### 第二轮：真实 echo / 预期工具错误 / status PASS

37 秒退出 0、未超时。仅从本机原始 JSON 事件提取以下允许字段及布尔断言，不展示完整原始 stdout/stderr：

| 顺序 | server / tool / 显式目标 | 实际结果 |
| --- | --- | --- |
| 1 | `hopnode / poc_probe / poc-local`，echo | `completed`；返回 message 精确匹配 `HOPNODE_P03_CODEX_20261019`，返回目标一致 |
| 2 | 同上，fail | `failed`，result.content 包含 `POC_EXPECTED_FAILURE`；预期工具业务错误，非 transport/error.message；后续 status 继续执行 |
| 3 | 同上，status | `completed`；返回目标一致，`active=0,canceled=0` |

恰好三个 hopnode 工具完成事件；其他 MCP server/tool 事件数 0，command_execution/file_change/web_search 事件数 0；最终消息含 `HOPNODE_P03_CODEX_20261019 COMPLETE`。

两轮透明 relay 均记录如下握手元数据（键顺序标准化）：

```json
{"event":"initialize_request","client_name":"codex-mcp-client","client_version":"0.153.4","protocol_version":"2025-06-18"}
{"event":"initialize_response","protocol_version":"2025-06-18"}
```

这直接证明本次 Codex 实际协议为 `2025-06-18`，与 SDK 测试客户端的 `2026-07-28` 分开记录。relay 位于 POC 自有 `stdio-relay/`，标准库实现，双向原字节转发，stderr 才写固定失败诊断；默认 trace 只允许 initialize 四类元数据。测试覆盖 CRLF、Unicode、EOF 无换行尾帧，以及工具参数/结果中的虚构敏感字段不会进入 trace。

### Codex 取消的有限尝试：未取得协议取消证据

第三轮使用相同 `-a never` / read-only / 临时 MCP 表和独立空工作目录，仅请求 `action=wait`；工具超时设为 120 秒，外层观察与中断在该时限内完成。增加中继 `--trace-cancellation`，仅允许记录 wait 和匹配取消通知的事件名，省略 ID、原因、参数和环境。

TTY 会话中观察到 `wait_call` 后，通过该会话 `write_stdin` 发送 Ctrl+C。会话 exit 1，之后自建 fixture/relay 进程数 0。但 trace 未观察到 `wait_cancel_notification`，stderr 未观察到固定 `P03_WAIT_CANCELED` 标记。**该尝试未能验证 Codex 协议取消，不记为 PASS；可靠的 Codex 取消验收仍 NOT_RUN。** 不能将终止进程或 SDK 的独立取消 PASS 代替客户端协议取消证据。
