## Linux race 首次失败与修复复测

同日集成方在 Linux 首次追加 `go test -race ./...` 检查，结果 **FAIL（DATA RACE）**。此前 Windows 普通 test/vet PASS 不足以发现该问题。原测试 `lockedBuffer` 匿名嵌入 `bytes.Buffer`，意外向外暴露其 `ReadFrom`；`os/exec` 的 `io.Copy` 走 `ReadFrom` 快路径，绕过包装器 `Write` 的锁，与测试中的 `text()` 并发读取发生竞争。

修复提交 `e030b1da9a4fe791b6a8fd5bd84aeb205650caf0` 将匿名嵌入改为未导出命名字段 `buffer bytes.Buffer`。仅由加锁的 `Write` 与 `text` 访问底层 buffer，不提供 `ReadFrom`，使 `io.Copy` 经过加锁的 `Write`。不改变协议服务或生产接口。

修复后在 POC 工作树重新执行：

## app-server 软中断预检：INCOMPLETE，模型轮次未发出

同日收到明确授权后，核对本机 `codex-cli 0.153.4 app-server --help`，运行 `app-server generate-json-schema --out <新TEMP>`，exit 0。实际本机 schema 定义 initialize/initialized、thread/start、turn/start、turn/interrupt（必需 threadId/turnId）及 turn/completed 的 interrupted 状态；仅有这些入口不能证明 MCP 取消会发生。未取得的官方网页不作为证据。

本轮临时 `appserver-cancel-probe.py` 仅显式 `--execute` 才运行：Windows native codex.exe、独立 stdio、空 TEMP、ephemeral thread；不使用现有 app/daemon/proxy/socket。向进程提交关闭 shell_tool/unified_exec/apps/multi_agent/web 的参数；保留 provider/auth，不复制 token、不改任何持久配置。模型前检查实际 readOnly/never 及 MCP 清单，清单不符即拒绝发 turn/start。没有模型轮次，不能据参数本身声称所有能力开关均已实际生效。计划中的 wait → turn/interrupt → 同实例 status 没有执行。未知事件、其他工具、任何审批/服务端请求、清单不符均拒绝继续；Windows Job 设置 kill-on-close 并查询 activeProcesses，但其分配时序仍有下述明确缺口。

| app-server 启动轮次 | 实际耗时 / 退出 | 守卫结果 | 模型与取消 |
| --- | --- | --- | --- |
| `run/` | 0.318s / exit 1 | initialize 响应后，驱动未识别已定义通知 remoteControl/status/changed；thread/start 请求已送出，但未完成其结果检查即停止 | turn/start=0；wait/interrupt/status NOT_RUN |
